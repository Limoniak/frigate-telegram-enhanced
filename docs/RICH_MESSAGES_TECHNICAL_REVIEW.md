# Telegram Rich Messages: technical review

**Review date:** 2026-10-27
**Branch base:** upstream `dev` at `27646bd`
**Scope:** Rich Messages, Telegram menu and snapshot picker UX. PR #48 remains separate.

## Implementation and evidence

- Existing text and media send methods are adapted to `sendRichMessage`; `EditRichMedia` calls `editMessageText` with a `rich_message` containing a media block and the existing callback buttons.
- New media is multipart uploaded using `attach://file`. Returned media IDs are read from the response's rich media block and reused for later edits.
- The event notifier retains its original chat and message IDs while replacing a snapshot with a video or animation. Caption and callback blocks are serialized with the replacement. The API-level test now checks `chat_id`, `message_id`, endpoint, multipart bytes, video block, caption, callback data, response message ID, and returned `file_id`.
- Per-message/per-chat locks serialize caption and media changes. Independent tracked messages are not held behind one global network lock. The late-caption test verifies an update uses the replacement media ID.
- A definitive edit rejection may fall back to a reply. An ambiguous timeout or server failure does not cause a second media send, avoiding a likely duplicate at the cost of possible missing delivery.
- `/menu` now renders a translated Cameras heading and description on separate lines. Pause labels use i18n keys in the six existing catalogs. `/snapshot` camera-picker callbacks use a new `S:<camera>` action and send a standalone snapshot; existing `s:<camera>` notification buttons keep their reply behavior.

## Telegram API contract

The current official Bot API changelog lists Rich Messages in 10.1, media blocks in 10.2, and rich button blocks in 10.3. `editMessageText` accepts a `rich_message`; `sendRichMessage` accepts rich content and reply parameters. Rich button rows have documented alignment and styling options, but no fixed width or client-independent color control. The implementation keeps left alignment and logical rows; Telegram clients determine the final visual treatment.

`ReplyParameters.allow_sending_without_reply` controls delivery when the target message is missing. `quote` supplies quoted text; it does not hide a reply quote. The Bot API has no general “suppress reply quote” field for ordinary messages. The `/snapshot` picker therefore drops its reply target, while notification “Now” continues to reply to the event that invoked it.

References: [Bot API changelog](https://core.telegram.org/bots/api#recent-changes), [ReplyParameters](https://core.telegram.org/bots/api#replyparameters), [InputRichBlockButtons](https://core.telegram.org/bots/api#inputrichblockbuttons), [RichMessageButton](https://core.telegram.org/bots/api#richmessagebutton), [sendRichMessage](https://core.telegram.org/bots/api#sendrichmessage), [editMessageText](https://core.telegram.org/bots/api#editmessagetext).

## Boundaries and limitations

- HTML conversion covers the tags generated by this app; it is not a general HTML converter.
- Ambiguous media-edit outcomes can leave the current `file_id` unknown. The code avoids reusing a stale snapshot ID that could revert the media.
- Exactly-once sending cannot be guaranteed after a lost response. The retry policy avoids replaying unique sends when Telegram may already have accepted them.
- In-flight media state is in memory. A restart during preparation does not recover the pending replacement.
- Large-video and GIF flows are tested with mocks/local processing, not uploads to Telegram or the real 50 MB boundary.
- No live Bot API endpoint or physical Telegram client was used in this QA pass.

## Release conclusion

Automated checks and mocks support review of request serialization, replacement, callbacks, and menu behavior. Live client rendering and Linux race/Docker checks remain external gates; see `RICH_MESSAGES_TEST_REPORT.md` and `RICH_MESSAGES_UI_QA.md`.
